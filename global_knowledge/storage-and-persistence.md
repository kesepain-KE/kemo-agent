# 存储与持久化功能说明

本文集中说明历史、记忆、运行状态、结构化日志和高频写盘的当前持久化规则。各章节保持独立职责，代码和数据库实现是事实来源。

## 历史对话 SQLite 存储

历史对话以每用户独立的 `users/<user>/history/history.sqlite3` 为唯一权威存储。旧式 `history/data.json`、`history/<window>/*.json` 和 `history/temp/<window>/*.json` 不再参与读取，也不会自动导入。

### 表职责

| 表 | 职责 |
|---|---|
| `history_windows` | archive 完整权威归档；旧版 runtime 行仅作为兼容快照保留，不再在每轮终态重写 |
| `history_sessions` | 会话卡片、生命周期、运行态、摘要与记忆任务状态 |
| `history_active_sessions` | Web、App、CLI 和外部消息入口的逻辑续接绑定；只指向仍为 open 的会话 |
| `history_web_leases` | schema v6 新增的兼容表名；当前按 session/client 保存 Web 页面与 App 设备/Socket 的在线到期时间，供跨进程判断是否仍有存活链接 |
| `history_deleted_sessions` | 已删除会话的持久删除栅栏，阻止迟到 Run 重新写入 |
| `history_deleted_windows` | 已删除物理窗口的 tombstone，阻止迟到 Run 复用旧窗口名；正常新窗口仍可使用当前会话 generation |
| `history_messages` | archive 用户/助手正文的唯一权威逐消息存储，用于还原正文、分页和内容搜索；避免与 archive `text_json` 重复保存 |
| `history_rounds` | archive 的逐轮思考、工具、Item 与用量指标；兼容旧 runtime 快照行，正常提交只追加 archive 新轮 |
| `history_context_summaries` | 独立于 runtime 行的增量上下文压缩摘要、覆盖轮次与记忆提取元数据 |
| `message_processed_messages` | 外部消息的领取、终态和错误；用于跨重启幂等 |
| `history_meta` | schema 与注册表修订元数据 |

数据库启用 WAL、外键检查、5 秒 busy timeout 和 `synchronous=NORMAL`。schema v3 会把旧 archive `text_json` 正文迁移到 `history_messages`，并把 archive/runtime 的 `round_metrics`、think、tool、items 大分区迁移到 `history_rounds`；schema v4 增加 `history_deleted_sessions` 删除栅栏；schema v5 增加 `history_deleted_windows` 物理窗口 tombstone。窗口 JSON 列只保留小型存储引用。正常追加一轮时只插入 archive 的新增消息后缀和一个新增 round 行；只有删除、撤回或编辑旧轮次时才重建对应 archive 增量行。每轮终态的 archive、上下文摘要、会话索引和活跃绑定仍在同一个 SQLite 事务中提交；事务成功后才更新进程内 runtime 工作区。archive 与 runtime 的逻辑路径继续作为稳定标识使用，但 runtime 路径默认只标识缓存键和摘要归属，不要求存在对应磁盘行。

### Runtime 工作区内存缓存

runtime 工作区是 archive 最近轮次的派生视图，不再作为每轮持久化主副本。进程内缓存最多保留 64 个窗口、单项最多 8 MiB、全局估算容量最多 64 MiB；同一用户最多驻留 16 个窗口且估算容量最多 16 MiB，先按用户配额、再按全局 LRU 淘汰，避免单个长会话或单个用户挤占全部运行内存。所有读取返回深拷贝。缓存版本由 archive 的 `updated_at + rounds` 组成；Web、CLI 或 Cron 其他进程提交新 archive 后，版本不匹配会立即丢弃旧缓存并从数据库重建，不能仅因内存中存在条目就继续使用。

加载顺序为：匹配版本的进程缓存 → 带匹配 archive 版本的旧磁盘 runtime 快照 → 直接从 archive SQL 表只读取最近 `agents.max_rounds` 轮。尾部重建会把绝对轮号转换为 runtime 本地 `1..N`，并在 `context.round_offset` 保存前置轮数，不会为重建加载完整长会话。旧 runtime 行不主动删除，也不再逐轮更新；版本不匹配时自然忽略。清空、删除、批量删除、重命名、底层窗口删除和 Cron 生命周期清理都会失效相关缓存，删除栅栏仍可阻止迟到 Run 从内存复活会话。

### 性能边界

- Web 历史列表默认跨 `web`、`cli`、`message:<platform>` 等来源读取当前用户的全部会话，并保留来源标签；结果按 `updated_at DESC, session_id DESC, source DESC` 稳定排序，分页默认每页 50 条、最大 100 条，使用由 `updated_at + session_id + source` 组成的不透明复合游标加载更早记录。`GET /api/users/{user}/sessions` 可传 `date=YYYY-MM-DD`，按 `Asia/Shanghai` 自然日直接过滤权威会话索引，并与来源、正文检索和游标分页组合使用；前端不会只过滤已加载的 50 条。
- Web 会话仍可切换和管理；CLI 与外部消息会话在网页中只读展示，避免网页接管仍由其他入口持有的活跃会话。写接口继续强制 `source=web`。
- 会话卡片返回记忆状态、已处理轮次、目标轮次、排队原因和最近失败信息。所有入口绑定到同一内部用户后，共用该用户的 `memory.sqlite3`，记忆页不按渠道过滤。
- 标题、摘要、会话 ID 和消息正文搜索直接查询表，不遍历历史目录。
- `history_search` 只读取已提交 archive 的 `history_messages.content_text`，因此字符串与多模态消息中的可见文本使用同一权威投影；保留原始 `message_index`，并排除删除栅栏命中的会话。工具支持 `source` / `session_id` 精确过滤，以及 `offset + next_offset + page_char_limit` 双边界分页，避免把大规模历史一次性塞进单个工具结果。上下文只返回 user/assistant 可见文本并逐条限长，不返回 system、tool、思考或工具日志。
- 活跃会话通过主键绑定恢复，不在启动阶段扫描全部归档。
- 完整正文只在打开指定会话、上下文构建、摘要或记忆整理时读取。
- 记忆处理状态使用 archive `data_json` 与 `history_sessions` 的小范围事务更新，不再重写 text/think/tool/items 大分区。

### Web 对话空间启动巡检与空空间生命周期

新建标签页与普通新建对话共用空会话回收规则。仅自动清理 `source='web'`、零轮、没有关联在线网页且
最后更新超过 90 秒的会话；不触及 CLI、APP、Cron、消息来源。零轮索引不是充分依据：存在任意归档消息、
archive/runtime 轮次、思考/工具/Item 数据或上下文摘要时保留；正在运行/排队以及记忆或摘要处理中的
会话也保留。即使取消/失败尚未形成完整轮，只要已经留下内容，就不会被当作空会话回收。

浏览器每 15 秒心跳，SQLite `history_web_leases`（历史兼容表名）使用独立 client 行、90 秒有效期，健康连续心跳约每
30 秒续写一次，其余请求只读检查。App 的 active/chat 请求和带会话范围的 WebSocket 使用同一持久租约；Socket 每 30 秒续租，断开时显式释放自己的租约。页面/设备内保留即时在线映射；持久租约用于跨进程及重启保护，不因
内存读缓存淘汰而丢失。关闭、切换或释放页面关联不会立即删除最后的租约检查点，它自然到期，避免
刷新/BFCache、乱序卸载通知和短暂网络抖动误删；多个标签页中任意一个保活即可保护会话。客户端
长时间冻结或断网到租约失效后视为离线，恢复页会提示已清理并解除绑定；尚未提交到服务端的输入
草稿不属于对话轮次。

Web 应用 lifespan 管理一个独立生命周期线程。每次 Web 后端启动只安排一次旧空间巡检：先等待 90 秒
在线心跳宽限，使重启前仍打开的标签页有机会重新登记；随后按用户、`updated_at + session_id` 游标、
每页最多 100 条遍历所有符合条件的旧空间。启动巡检完成后，线程每 60 秒继续执行同一离线空间裁决；有数据且租约已过期的 Web 空间以 `offline_session_expired`、App 空间以 `offline_app_session_expired` 关闭并进入记忆队列；Web 完全空的空间继续事务删除，App 空预留只关闭不删除；
后端关闭时停止线程。只访问已有历史数据库，不为无历史用户新建数据库。返回与进程内状态只保留各类
最多 20 个会话 ID/错误类型样本，计数不截断，不长期保存全量会话列表。

启动巡检的候选必须同时满足：`source='web'`、最后更新至少 90 秒、没有未过期持久租约、没有当前服务
保护的页面或 ActiveRun，并且不处于运行/排队、记忆处理或摘要处理状态。每个候选仍尝试非阻塞会话锁，
并在 SQLite 写事务内再次核验；启动期间新到达的页面先续租则跳过该空间。App 候选使用同一 90 秒空闲阈值和持久租约，但保持 `source=app` 分区。已关闭且记忆已覆盖全部提交
轮次的历史不重复登记；已处于 `queued` 的任务由维护器继续恢复，不在每次启动重复写队列。

有真实对话数据的旧空间不会被删除。巡检会把仍处于 open 的空间转为 closed、解除所有 active-session
绑定。Web 启动首轮以 `startup_offline_session`、后续周期裁决以 `offline_session_expired`；App 分别使用 `startup_offline_app_session` / `offline_app_session_expired` 原因登记到既有记忆提取队列。队列登记只更新持久状态，不在
生命周期线程中调用模型；登记成功后通过 `MaintenanceScheduler.wake()` 中断当前轮询等待，
由原维护线程领取并转换记忆。已有记忆游标继续生效，不重复提取已完成轮次。显式配置
`memory.extraction_mode=disabled`、没有完整提交轮次、缺少有效 archive 或已经处理完毕时，队列返回对应
跳过原因：空间仍作为关闭历史保留，不按空空间删除，也不伪装成已经转换。队列登记失败只记录异常类型，
不会删除原对话；后续周期巡检可再次尝试。

“有数据”不只依赖会话表的 rounds 计数，还检查 archive/runtime 消息、逐轮 think/tool/item/metric 数据
和上下文摘要。因此索引计数异常、取消/失败留下的部分内容也会保留。无任何上述内容的旧空间走空空间
事务清理；周期巡检对有数据历史只执行关闭、解绑和记忆入队，绝不删除其 archive 或消息。

回收不是即时删除。一次正常启动会在约第 90 秒完成首轮判断；之后新产生的空空间通常在最后一次持久
心跳后约 90–150 秒删除；有数据空间在同一时间尺度关闭并入队，积压候选或忙会话可能延后。过期租约分批清除，没有变化时不写心跳快照或
清理日志。

清理先跳过当前服务在线页面/活跃 Run，再尝试获取会话执行锁，并在 `BEGIN IMMEDIATE` 内重新检查
真实数据与租约。续租和清理串行裁决；在线续租先提交则跳过，删除先提交则后续租约返回 404，不重建。
会话、活跃绑定、空物理窗口及租约一并事务删除，保留原有会话/窗口删除栅栏防止迟到写入复活；失败
回滚，诊断仅记录错误类型。schema v5 升 v6 是增加租约表和索引，不删除或改写存量对话内容。

已关闭或已清理空间不能被迟到心跳、active-session 恢复、CLI `/use` 或旧 `?session=<id>` 链接隐式重建。核心追加入口也会拒绝 closed/deleted 会话，避免绕过页面状态把历史重新改成 open。旧页收到 404 后
保持解除绑定状态，不自动创建替代空间。只有用户显式进入新的对话页面状态，例如打开
`/chat?user=<user>&new_session=1`（包括左下角“新建此用户标签页”入口）、使用正常新建对话动作/首次发送，
或调用会话创建 API，才会预留一个新的随机会话 ID；它不会复用被清理的旧 ID。
有数据但被启动巡检关闭的空间继续出现在历史列表中，可查看其原始记录，但不会作为无参数页面的活跃
绑定自动恢复。

使用 `--no-host` 或关闭后台调度时，启动巡检仍会持久登记 `queued`，但不会在生命周期线程内自行执行
模型；任务会一直保留，直到带 MaintenanceScheduler 的 RuntimeHost 可用。此边界避免 Web 清理线程绕过
统一模型并发、取消、凭据和记忆幂等规则。

### 非 Web 会话的生命周期兜底

CLI 使用独立 `source=cli` 与 `cli:<user>` 活跃绑定，不再借用 Web 会话；单次请求、交互退出、KeyboardInterrupt 或处理异常后，都会 best-effort 地先登记
`queue_memory_extraction`，再调用 `close_session`。交互模式使用 `/new` 或 `/use` 切离当前空间时，先收尾当前会话；`/use` 只接受仍为 open 的已有 CLI 会话，不把不存在的 ID 当作新建。下次默认启动会创建新会话；显式给出已经 closed 的 ID 也不能继续追加。收尾异常被隔离，不改变 CLI 原始退出码。Cron 的
`exec_mode=agent` 主智能体任务在 `handle_request` 返回或抛错后执行相同收尾，来源固定为
`background:cron:<task_id>`；`subagent` 与 `function` 分支不创建伪造的主会话。

RuntimeHost 每小时调度系统任务 `session_lifecycle_sweep`，默认处理闲置超过 24 小时的所有来源会话，
单轮最多 50 个。`cron.session_idle_close_seconds` 只能在全局配置中覆盖阈值（最小 3600 秒）；运行/排队/
停止中的会话、未过期 `history_web_leases` 兼容租约保护的 Web/App 会话、无法确认租约状态或无法取得会话锁的会话
都会跳过，其中 Web 与 App 都以持久租约代表跨进程存活链接。扫描只关闭逻辑会话并写入记忆提取队列，不删除 archive/runtime 窗口、消息或历史索引；每个
候选的异常单独记录，后续候选继续执行。若首次“入队后关闭”中的入队步骤异常，关闭记录不会永久丢失：后续巡检会识别 closed 且仍有未处理轮次、状态又未处于 queued/processing/failed/completed/disabled 的会话，补登记记忆队列并报告 `requeued_closed`。已由维护器领取或失败重试的会话不重复抢占。

### 运维规则

- 不直接编辑数据库或把 JSON 文件放入 history 目录尝试恢复历史。
- 删除会话必须同时清理 session、window、message 和 active 记录，应调用框架 API。框架会额外留下短小的 `history_deleted_sessions` 栅栏，防止删除发生时已经在运行的旧 Run 迟到提交；只有显式重新预留同一逻辑 ID 时才会清除栅栏。
- 运行中备份使用 SQLite backup API 或先完整停止框架；只复制 `history.sqlite3` 而漏掉 `-wal` 可能得到不完整快照。
- schema v3/v4/v5 迁移释放的旧 JSON 页会先进入 SQLite freelist 并被后续写入复用；为避免升级时长时间独占数据库，框架不会自动执行 `VACUUM`。确需立即缩小物理文件时，应停止框架、完成备份后再由运维显式执行。
- 上下文摘要不是历史正文；终态提交时与 archive 和会话索引在同一事务更新，runtime 内存工作区只在事务成功后切换。不要重新创建 `context_summary.json`。
- schema 不兼容时应明确失败或执行专用迁移，禁止静默混读两套历史格式。

### 定时任务历史的自动清理

仅 `source=background:cron:<非空 task_id>` 的 `agent` 定时任务对话具有自动生命周期。执行终态在 `history_sessions.record_json.cron_finished_at` 保存完成时间；默认从该时间起保留 7 天。旧记录没有此字段时使用 `history_sessions.updated_at`，后续标题或摘要更新不会延长已经具有完成时间的新记录。配置、范围、网页入口和调度规则见 `configuration-reference.md` 与 `task-automation.md`。

Maintenance 每个用户、每个五分钟窗口最多处理 100 个候选。只读选择后，以非阻塞会话锁避免干扰本进程活跃 Run，再在 `BEGIN IMMEDIATE` 事务内重新检查来源、完成时间、`run_state`、记忆状态和摘要状态。事务删除 `history_sessions`、`history_active_sessions`、archive/runtime `history_windows`、`history_messages`、`history_rounds` 和 `history_context_summaries`，任一 SQL 失败整体回滚；没有历史数据库的用户不会为了空扫描创建数据库。

删除会写逻辑会话和物理窗口 tombstone。它们只保存身份与删除时间，不保留正文，用于拒绝已经在途的旧提交。每次 Cron 主智能体执行使用新的逻辑会话 ID，不复用已删除会话；被删除的旧物理窗口持续保持封锁。任务定义、`runtime/logs.sqlite3` 执行记录、附件、下载文件、消息队列和非 Cron 会话均不在自动清理事务中。

## 记忆 SQLite 存储

四档记忆以每用户独立的 `users/<user>/improve/memory.sqlite3` 为唯一权威存储。旧式 Markdown 碎片、三层 `data.json`、`storage.json`、`.memory_operations.json` 和 `important_view.json` 不再参与读取，也不会自动导入。`memory_temporary_important.md` 仍是位于用户根目录的可重建热视图，不是权威数据库或第五个生命周期层。

### 为什么独立建库

记忆与历史采用两个数据库：`improve/memory.sqlite3` 和 `history/history.sqlite3`。二者的写入频率、保留周期和维护任务不同，分库可避免记忆加权与聊天归档争用同一写锁，也便于单独备份、诊断和重建。

数据库启用 WAL、`synchronous=NORMAL`、外键、5 秒 busy timeout 和显式写事务。连接、Schema 与业务规则统一归入 `run/memory/` 领域，生产代码只通过该领域入口的条目级接口读取或修改记忆，不再提供模拟旧 `data.json` 的 `load_index`、`write_index`、层级目录或正文文件路径接口，外部代码不得直接拼 SQL 修改生命周期状态。

### 表结构

| 表 | 用途 | 关键约束 |
|---|---|---|
| `memory_meta` | schema 与派生视图元数据 | `key` 主键 |
| `memory_fragments` | 四档正文和生命周期 | `filename_key` 全局唯一；tier 枚举；权重非负；永久层无 `expires_at` |
| `memory_weight_events` | 用户历史/人工更新的日锁与加权记录；creation 只占日锁、不加分 | `(fragment_id, evidence_date)` 主键，数据库强制每日最多一次 |
| `memory_operations` | 批量提取幂等结果 | `operation_id` 主键，重复批次只重放结果 |
| `memory_important_sources` | 临时重要热视图引用 | 每个临时源最多一条，并保存内容摘要用于失效判断 |

`filename` 保留 `.md` 后缀只是稳定的逻辑身份和 UI 展示合同，不表示磁盘上存在对应 Markdown。跨层同名由数据库唯一约束拒绝，晋升直接更新同一行的 tier，不复制正文文件。

### 生命周期与事务

- 新的非明确候选进入 `seven_days`；用户明确要求长期记住的候选可直接进入 `permanent`。
- 同名临时候选更新正文后，生命周期到期时间不滑动；用户历史证据按原轮次的上海自然日写入 `memory_weight_events`，每个证据日最多加一（初建首日仅登记不加分）。
- 到期且达到阈值时，在一个事务内更新 tier、重置权重和加权事件、写入新的固定到期时间；未达阈值则事务化删除。
- 语义融合会在同一事务内更新目标正文和生命周期、删除来源；任何一步失败都会回滚。
- 永久层不累计权重且无到期时间，普通非明确候选不能覆盖永久正文。

Prompt 注入、Web 浏览、`memory_manage` 搜索和用户主动查看均为只读操作，不写加权事件。保存、手动压缩、Token 超限压缩及配置启用的 background / on_commit 历史管线提供原始用户证据。用户主动修改正文（Web / memory_manage edit）或手动审阅更新是明确的人工维护入口，按执行日使用同一日锁；并非只读检索产生加权。

### 碎片粒度与分类

`self_improve` 先枚举输入中全部具有长期价值的信息，再分两类判断哪些内容确实不可分割。
**碎片数量由独立事实数量决定，字符数只做防失控检查，不能作为继续合并的理由。**

每项信息依次检查四个边界：能否独立更新、能否独立失效、再次出现时能否独立加权、搜索时能否独立取回。
任意一个边界可以独立处理，就必须拆成单独碎片；只有四项都必须共同变化、拆开会破坏关系时，才允许组成 A 类特征簇。

| 类型 | 适用 | 粒度规则 |
|---|---|---|
| **A 类：画像与特征簇** | 描述“用户是谁”的长期特征：人格、精神状态、审美偏好、经济状况、学习与技能、项目与工作方式、环境与设备 | 大维度只用于分类；只有同一稳定子主题且更新、失效、加权、检索边界完全一致时才可合并。1000 字只是异常防失控硬上限，不是填充目标，跨维度禁止合并 |
| **B 类：事实与规则** | 具体决定、规则、参数、约定和结论 | 一个事实一条碎片，正文 ≤ 100 字（确需上下文可放宽到 150 字） |

同一边界也适用于用户通过 `memory_manage add/edit` 的手动写入：不显式声明类型时正文不得超过 B 类 150 字硬上限；超过 150 字必须声明 `memory_type=A`，且仍不得超过 1000 字。显式声明 `memory_type=B` 时超过 150 字直接拒绝。`important` 热画像由运行时维护，`memory_manage` 对该层只开放读取和搜索，不能直接新增、编辑或删除。

A 类的维度表。命中关键词**只用于维度归类，不用于判定能否合并**：

| 维度 | 参考关键词 |
|---|---|
| 身份与背景 | 身份、年龄、学历、家庭、所在地、作息 |
| 人格与精神结构 | 人格、精神状态、心本、灵宝、自我认知、哲学观 |
| 审美与偏好 | 喜欢、不喜欢、审美、风格、口味、忌讳 |
| 经济状况 | 生活费、消费、成本、订阅、余额 |
| 学习与技能 | 学习、掌握、进度、教程、新手 |
| 项目与工作方式 | 项目、架构偏好、工作方式、流程 |
| 环境与设备 | 环境、设备、工具链、硬件、系统 |

出现表中没有的新维度时新建独立子主题，不得塞进已有容器。同属「审美与偏好」或「项目与工作方式」等大维度不代表可以合并；回答语言、界面留白、Git 提交边界、实际测试责任等能够分别变化的内容必须分别成条。B 类文件名只覆盖该事实，禁止「xxx 汇总」「xxx 总览」式容器标题。

#### 晋升时超限拆分

记忆晋升不是把碎片内容简单累加搬运，而是让它以合适粒度进入新档位。碎片晋升前检查正文长度，**超出该类型上限（A 类 1000 字 / B 类 100 字）时必须先拆开再存进目标档位**：

- A 类按维度内**子主题**拆，**不设总纲**（同层内后续会重新融合，不必预留汇总位）；B 类按**独立事实**拆，一个事实一条。
- 子碎片**就地留在目标档位**，不跨层移动；需要换层时由用户主动调整。
- 继承源碎片的 `expires_at` 与 `tier_entered_at`，**不重算时效**——拆分是同一份记忆的切分，不是新记忆。
- 权重按新档位规则从 0 起算（与直接晋升一致）；拆分本身**不产生加权事件**。
- `split_into` 与 `merged_with` 同时出现时优先执行拆分并记录告警。子碎片文件名继续受全局 `filename_key` 唯一约束；已有同名不会被覆盖，而是按 `-2`、`-3` 后缀生成可用名称。
- **防震荡**：拆分后同层内允许再次融合，但融合结果**永不跨越上限**；到上限即停止合并，稳定在「多条、各自达标」。
- 只返回决策，多条落盘由 cron 在同一事务内完成。
- 该拆分挂在**晋升链路**（action=`memory_promotion`）上，不并入热画像任务 `daily_consolidate`。
- 每项晋升决策必须显式返回 `memory_type: "A" | "B"`。`split_into` 子项默认继承顶层类型，类型不同时可单独声明。模型决策不是唯一防线：SQLite 落盘前会再次检查，B 类通常应控制在 100 字且绝不超过 150 字，A 类绝不超过 1000 字；正文超过 150 字但没有显式声明 A 类、融合后超限或任一拆分子片超限时，本次晋升拒绝、整项不落盘，来源碎片保留等待下次巡检。

**计数口径**：提取按独立事实计数，不按对话轮数或单文件字符数折算——一轮中识别出几个合格事实就产出几条候选。运行时不再使用 `round_count × 2` 或固定单轮条数截断，只受 `memory.extraction_max_candidates_per_batch` 和框架硬上限约束。达到上限时保留价值最高、证据最明确的独立事实并报告截断，不得把剩余事实压进大文件。晋升融合只在同一事实的更新版之间进行（如“生活费 1500→2000”）；主题相近但事实不同的碎片各自独立成条，不得融合。

文件名提示词建议 ≤ 20 字符，运行时字段上限 `FILENAME_MAX_CHARS` 为 50；两者刻意不对称，为 LLM 输出不稳定留余量，不得强行对齐。

### 搜索命中与每日加权

`self_improve` 先把每个候选提炼为 2～4 个核心关键词，再通过 `memory_manage search_many tier=all`
批量搜索：不超过 20 个候选时一次查询，超过 20 个时按最多 20 个一批分组。搜索优先规范化完整短语；模糊查询使用英文词、中文关键词和 bigram 计算覆盖率，
多片段查询至少命中两个有效片段且覆盖率不低于 50%，单个较长中文片段要求至少两个 bigram
且覆盖率不低于 60%。单个公共词不能直接证明两个碎片语义相同。

搜索结果返回 `match_score`、`match_coverage`、`matched_by`、`matched_terms` 和 `exact_match`。
子代理必须结合完整正文确认语义一致，并返回检索命中的 `memory_ref` 与 `filename`。
`self_improve` 的 `search_many` 强制 `include_content=true`；仍只授权只读搜索和必要的技能创建，
无须增开权重写入工具。宿主在 SQLite 事务中负责实际修改：

| 候选 action | 宿主行为 |
|---|---|
| `create` | 新建事实，同名冲突拒绝，不能覆盖旧碎片 |
| `reinforce` | 旧事实再次被证明，只加权、不接受正文替换 |
| `revise` | 旧事实被修正，写入完整新正文，并按证据登记权重 |
| `forget` | 后台提取须显式遗忘与用户原话证据；已有目标同样绑定检索引用 |
| 兼容 `upsert` | 新目标转 create；旧目标绑定真实搜索回执后按正文是否变化转 reinforce / revise |

每个旧目标都必须在本次成功的 `memory_manage search_many` 完整正文回执中出现；执行器依据
回执注入内容 SHA-256（忽略模型自行给出的哈希），落盘前同时检查 tier、filename 与内容摘要。
缺少回执、引用不一致、正文或层级已变化的候选拒绝，不盲改。用户主动 `manual_review` 的旧目标
同样遵守检索绑定，但不强制套用历史轮次证据格式。引用校验只能证明目标和快照一致，
**不能保证模型的语义判断永远正确**；公共关键词或高匹配分数仍不等于同一事实。

`search_many` 在一次调用中只加载一次目标记忆层，再在内存中处理最多 20 个查询，不会随候选
数量重复访问四层数据库。该路径面向数百至数千碎片；单项搜索同样使用相同评分规则和全局排序。

### 原证据日期、幂等与可观测性

- 每个后台候选提供 `durable=true`、`evidence` 用户原话及 `evidence_rounds`。宿主验证引文在
  每个指定轮次的一条用户消息内完整出现；不能跨消息拼凑，也不能使用助手或工具文本。
  旧候选省略轮次时仅推断精确命中的轮次；同名候选在持久化时合并已经验证的证据轮次。
- 新成功轮次在 `round_metrics` 保存 UTC、带时区的 `committed_at`，归档和恢复保留此值。
  宿主转换为 **Asia/Shanghai 成功提交日期**，模型不决定日期；处理发生在哪一天不影响证据日期。
  长耗时对话跨午夜时，以成功提交日为准，不声称是用户开始输入的日期。
- 旧轮次缺少可信时间戳、时间无时区、非法或位于未来时，可保存有效正文，但不伪造历史加权；
  返回 `missing_evidence_date`。历史消息表的 `created_at` 可能是窗口创建时间，**不得据此回填**。
  本次修复不扫描或批量改写用户旧记忆权重。
- 首次证据创建碎片时 weight=0，登记 `reason=creation` 占据其日期的日锁；该事件不是 +1。
  新片批量获得四个不同日期的可信证据时，首次为 0、后三日各 +1，最终为 3。
  同一天跨批次再次出现不重复加分；不能把事件总行数直接当作权重。
- 当前档位首次 creation 日期是可接纳历史证据的下界；没有该登记的旧片使用进入档位日期。
  更早的乱序证据保守跳过并返回 `outside_tier_evidence_window`，不重置生命期或倒推创建时间。
  入库和晋升的固定到期时间仍基于实际入库/进入档位时间，未改成回溯历史时间。
- 普通晋升会清空原档位事件并重置权重；早于新档位进入日的证据不能再次加分。
  拆分晋升维持既有的生命周期继承契约，子片证据下界使用继承的 tier_entered_at，不另造晋升时间。
  `last_weight_date` 为本档位最新的已加权证据日期，乱序补提取不能让它倒退；
  真正去重依据是 `(fragment_id, evidence_date)`，不是单个 last_weight_date 字段。
- on_commit、补提取和后台恢复使用稳定批次 `operation_id`，只哈希用户证据、轮次与提交时间，
  不因助手/工具序列化差异改变身份。操作结果与碎片修改同事务提交。
  同一批次返回 `replayed=true` 时只是旧回执，不代表本次又加了权重；不同批次边界仍由日锁兜底。
- 结果区分 `created`、`updated`、`content_updated`、`weighted`（发生实际 +1 的文件）、
  `daily_locked`、`weight_events`（逐证据日期的 +1）、`weight_skipped` 和 `rejection_reasons`；
  `candidate_filter` 报告执行器过滤原因，缺少日期不是静默当作今天加权。
- Web 详情由后端返回 `weighted_today`（今日证据实际 +1）与 `weight_locked_today`（包括 creation
  的今日已登记），并附 `weight_day` / `weight_timezone`。前端不再用 UTC 日期猜上海日锁，
  不再把历史加权一概描述为“因编辑增加”。运行状态维护栏按实际处理时间包含纯加权更新，
  不要求正文修改；`weight_increments` 排除 creation。日锁事件随档位晋升/删除清除，
  该列表是当前碎片状态视图，不是永久审计日志。

### 临时重要热视图

数据流固定为：

```text
用户对话历史 → 临时三层表行 → memory_temporary_important.md
```

后台整理临时三层时禁止把 `memory_temporary_important.md` 作为输入证据。热视图发布时，`memory_important_sources` 记录来源行和内容摘要；该关系只负责热视图失效判断，不过滤普通临时记忆的 Prompt 注入。来源碎片始终在原层按数量上限正常注入，热视图只作为更高优先级的强化概括。来源内容被修改、删除、转为永久层或到期时，旧热视图视为失效，普通临时层继续按自己的规则处理，等待后台更新。临时层间正常晋升且内容未变、期限有效不单独导致失效。主动查看仍可读取旧文件，查看本身不加权。

### 临时重要记忆的生命周期与页面状态

`MemoryStore.important_view_status()` 以一致的只读 SQLite 快照检查来源数量、内容摘要、所在层级和有效期；
`important_view_is_current()`、来源读取和 Web 读写接口使用同一判定。到期判断不必等待清理任务先删除来源。
校验不会删除正文、加权或刷新来源关系，损坏的来源数量记录按失效处理。

`GET/PUT /api/users/{user}/memory/important` 返回 `lifecycle`：
`status`（`valid`/`invalid`/`untracked`/`empty`）、`is_current`、`reason_codes`、简短 `reason` 和 `prompt_eligible`。
失效原因包括“来源内容已更新”“来源记忆已删除或清理”“来源已转为长期记忆”“来源记忆已到期”“来源记录异常”；
多个原因可合并，不回显源正文、文件名或 SQL。已删除来源没有历史原因记录时，不猜测是人工删除还是到期清理。

旧版或手写文件没有来源记录时显示“未校验”，保留原有兼容注入行为，不伪称已验证有效；空正文显示“暂无内容”。
`prompt_eligible` 表示当前有效性与注入预算允许后续构建使用，不代表当前 Run 已实际注入；关闭预算不等于记忆失效。
人格/记忆静态 Prompt 在 Run 开始时构建，页面发现失效不会追改正在执行的 Run 快照。

网页在临时重要记忆卡片及编辑区显示状态，失效时给出短原因和“后续对话暂停注入、旧内容保留”的提示。
记忆页前台每 15 秒重读一次（后台标签不主动轮询），也可手动重新读取；状态请求失败显示“状态未知”，不沿用缓存的有效结论。
刷新不会覆盖未保存编辑。人工保存热画像只改正文，不重置来源摘要或自动恢复有效；正常后台更新并重新记录来源后，页面重新校验恢复状态。

热视图巡检不能一次性返回整个大型层级。`memory_temporary_important` 使用 `memory_manage list(limit=500, offset, compact=true, include_content=true, page_char_limit=80000)` 按“条目数 + 序列化字符数”双重边界分页读取三层临时记忆和永久记忆，正文随列表批量返回，不再对全部碎片逐条 `get`。沿 `next_offset` 读取到 `has_more=false` 且累计数量等于 `total` 后才能发布新热视图；否则必须保持旧视图，不得基于局部数据执行永久协调或清理。

热视图文件正文尽量保持在 `important_memory_max_chars`（默认 20000）以内，该值只控制 Prompt
注入预算。`important_memory_output_max_chars` 是语义独立的输出防失控硬上限，当前默认同为
20000；超过输出上限时拒绝本次更新且保留旧视图。

### 模板、升级与旧格式

`template/user/improve/` 只包含 `.gitkeep`，不得提交预生成的二进制数据库。`user_create.py` 在真实用户目录落地后初始化 schema；更新器也只初始化缺失数据库，不导入或删除部署者的旧文件。当前源代码旧记忆已被抛弃；需要保留旧部署数据时，应在升级前自行导出，不能假定框架会自动迁移。

### 备份与维护

- 最稳妥的备份方式是停止写入后复制整个 `improve/`，或在运行中使用 SQLite backup API。
- WAL 模式运行时不能只复制 `memory.sqlite3` 而忽略尚未 checkpoint 的 WAL。
- 不提交 `memory.sqlite3`、`-wal` 或 `-shm` 到模板或 Git。
- 完整性检查使用 `MemoryStore.integrity_issues()`；不要通过手工编辑数据库修复生产数据。

## 运行状态 SQLite 存储

框架把高频变化、需要事务一致性或索引查询的状态分配到三个 SQLite 数据库。配置、附件、模块清单和持久消息队列仍保留文件形式，不能为了统一而盲目入表。

### 数据库分工

| 数据库 | 表 | 权威数据 |
|---|---|---|
| `users/<user>/history/history.sqlite3` | `history_context_summaries` | runtime 上下文摘要、绝对覆盖轮次与摘要内存提取元数据 |
| 同上 | `message_processed_messages` | 外部消息幂等键的 processing/completed/failed 状态 |
| `users/<user>/task_plan/task_plans.sqlite3` | `task_plans`、`task_plan_steps`、`task_plan_dependencies` | 任务计划元数据、步骤和有序依赖 |
| `runtime/logs.sqlite3` | `message_route_state` | 外部消息模块健康、计数、延迟和输入线程状态 |

上下文摘要与对应 runtime 窗口裁剪在一个 `history.sqlite3` 写事务中提交。手动压缩只有在窗口轮数、偏移、摘要哈希和覆盖轮次全部回读一致后才报告成功；失败时同一事务恢复旧窗口和摘要。

外部消息领取使用 `BEGIN IMMEDIATE`：批次内任一幂等键已存在时整批拒绝，不留下半批 processing。保留上限只淘汰最旧终态记录，绝不删除处理中记录；宿主启动时把遗留 processing 改为 failed，避免重复执行副作用。

任务计划通过 revision 防止旧副本覆盖新状态。步骤参数、结果和错误允许以表内 JSON 列保存任意结构，但步骤身份、顺序、状态及依赖必须是可索引行。

### 文件边界

- `message.md` 与 `.processing.md` 是插件和核心之间的持久消息队列。
- 附件目录只保存消息附件，不保存结构化状态。
- `template/task_plan/plan_template.json` 只说明任务输入 Schema，不复制到用户目录。
- Cron 定义、用户配置、模块清单与资源文件继续按各自合同存储。

运行时不扫描其他文件格式来迁移、回退读取或双写这些状态。更新器只初始化当前数据库 Schema。

在线备份必须使用 SQLite backup API；离线复制应先完整停止框架，并连同 WAL 相关文件一起处理。不要直接编辑数据库。

## 结构化运行日志存储

### 单一事实来源

运行日志统一存放在项目运行目录的 `runtime/logs.sqlite3`：

| 类型 | 表 | 内容 |
|------|----|------|
| Cron 执行记录 | `cron_execution_logs` | 用户、任务、时间、状态、耗时、结果摘要与错误 |
| 外部消息路由记录 | `message_route_logs` | 入站、出站、附件元数据与失败状态 |
| 外部消息模块状态 | `message_route_state` | 健康、收发计数、延迟、输入线程状态与平台扩展字段 |

进程启动和重启等纯诊断输出仍可使用普通文本日志。Cron 任务定义仍是任务配置文件；附件仍在模块附件目录。运行日志数据库不是聊天历史库，也不保存附件二进制。

### 写入与查询规则

数据库使用 Python 标准库 `sqlite3`，启用 WAL、忙等待、事务和时间索引，允许 RuntimeHost、Cron、消息路由与 Web 并发访问。Cron 记录同时提供 `user + task_id + occurred_at` 联合索引，单任务历史必须在 SQL 过滤后再应用条数上限，不能先截取用户总记录再用 Python 筛选。网页只查询表，不扫描模块目录或 Cron 目录寻找日志文件。

保留期清理每天至多执行一次。若清理确实删除了记录，且数据库至少 64 MiB、空闲页达到 25%、距离上次压缩至少 7 天，日志存储会在同一进程锁保护下执行一次受控 `VACUUM` 回收文件空间；压缩失败只影响空间回收，不影响 Cron 或消息写入。

每个事件根据稳定业务字段生成幂等键，重复提交不会制造重复行。写入失败属于可观测性故障，不得重放已经执行的任务或已经发送的消息；路由状态事务失败则必须显式报告，不能伪装为状态已更新。

默认保留 90 天，可通过 `KEMO_LOG_RETENTION_DAYS` 修改；设置为 `0` 表示不自动清理。清理只删除事件表中的过期记录，不删除聊天历史、任务定义、消息队列或附件。

### 运行状态页分类执行记录

`GET /api/users/{user}/runtime/logs` 独立提供近期日志，不重新聚合 Prompt、记忆、Token 和整页运行状态。参数为 `category=all|backend|threads|terminal|message`、`page`（从 1 开始）、`page_size`（默认 25，上限 100）、`refresh`（默认 false，true 强制绕过读取缓存）。返回 entries、counts、分页、生成时间、cache 和 source_errors；除 `terminal` 外，页码超过当前记录窗口时回到最后一页。

- **全部**：合并以下来源的有界近期视图，不是全量历史日志。各分类数量也仅代表此窗口。
- **后端日志**：当前用户和 `__system__` 的 Cron 持久化记录，以及当前进程观察到的工具调用（包括 shell）与 RuntimeHost 组件生命周期摘要；不是原始 Python/服务器文本日志。高频成功和内容相同的连续 partial 可能以聚合记录出现，新的异常指纹与恢复仍即时可见。
- **后端线程**：当前后端进程最多 200 个线程的即时快照，仅含线程 ID、存活/守护状态和通用类别，不保存轮询快照，不展示自定义线程名、栈和局部变量，也不声称是历史执行轨迹。
- **终端日志**：`start_web.py` 启动 kemo-agent 时用户可见终端的标准输出与标准错误快照，不是 shell 工具日志。启动入口会在保留原终端显示的同时按行收集输出；ANSI 控制字符会移除，常见 API Key、Token、Cookie、密码、Authorization/Bearer 与 URL 密码形态会脱敏。未换行的单条输出在收集器内也只保留 1001 字符，最终展示为最多 1000 字符加省略号，避免异常长行让进程内 pending 缓冲无限增长。终端分类是单个只读、按时间正序的实时输出页：不分页，历史行在上、新输出在底部动态出现；前台每 2 秒只读取并渲染最近 300 行，达到窗口上限后自动丢弃浏览器侧最旧行，避免全量缓冲区卡顿。用户向上滚动时不强制拉回底部。日志仅在当前进程内存中保留，重启后以新启动终端重新开始；不写入 SQLite，也不能补录启动前或其他进程的终端内容。shell 工具调用仍归入“后端日志”摘要，完整命令及输出不进入此页面。
- **消息日志**：当前用户的消息平台、方向、类型和成功状态；不读取或复制消息正文、聊天标识、附件路径和凭据。

读取策略：SQLite 分别按索引选取最多 200 条合并 Cron 与 200 条消息投影，不解析大结果/错误 JSON。投影按规范化项目根目录和用户隔离，缓存 5 秒，最多 16 个 LRU 桶；并发缓存缺失合并查询，返回深拷贝。同进程 Cron/消息写入、消息删除在事务提交后失效缓存；其他进程写入最多经过 5 秒读取缓存窗口可见。源读取失败不缓存为空成功，页面显示简短的来源不可用提示。

新增诊断摘要只在进程内保留：全进程最多 2048 条、最长 1 小时，读取时清除过期记录，满容量淘汰最旧记录，重启丢失，不写入 SQLite。存量任务失败、消息记录、对话终态的立即持久化规则不变。本缓存不是可靠审计日志，也不削弱已有持久化保障。

除终端分类外，网页分类、翻页和刷新使用独立查询，前台每 10 秒刷新，后台页面不定时轮询；终端分类使用无分页的实时输出视图，前台每 2 秒刷新。切换用户不沿用旧用户展示数据。刷新日志强制绕过服务端 TTL，不触发整页聚合。

### 安全与维护

消息正文和外部平台标识属于敏感运行数据。`runtime/` 必须保持 Git 忽略，部署时应限制数据库文件的本地访问权限，不得把 Token、Cookie 或平台密钥写入日志。

在线备份应使用 SQLite backup API；离线复制必须先完整停止框架，并连同 WAL 相关文件一起处理。不要直接编辑数据库。

## Python 持久化写盘策略

### 多用户有界读取缓存

`run.infra.BoundedReadCache` 是可丢弃的读快照基础设施，不是数据库、任务队列或运行态存储。命名空间由缓存实例隔离，键包含规范化路径或服务实例内的用户/来源/会话；Windows 使用系统路径大小写规则，Linux 不折叠大小写。调用者必须先执行用户存在性、权限、路径包含及链接校验，不能把缓存命中视为授权。

| 接入点 | 总条目 / 估算容量 | TTL 与失效 |
|---|---|---|
| 配置 JSON 文本、人格/手册/技能/插件提示词、拓展/感知元数据与数据、子代理包源文件 | 512 / 16 MiB；同用户最多 64 条、4 MiB；单文件超过 512 KiB 不缓存 | 每次校验 mtime_ns、ctime_ns、大小、inode、device、mode；最多 5 秒；Web 原子写入及公共原子替换成功后显式失效 |
| Cron 持久化任务列表 | 128 / 8 MiB；每个任务目录一个桶、最多 2 MiB | 每次扫描任务文件成员和元数据签名，最多 30 秒；创建/修改/删除/迁移失效；只缓存磁盘定义，每次叠加实时运行态 |
| 执行日志投影 | 16 / 8 MiB；每个根目录+用户一个桶、最多 2 MiB | 5 秒；提交后失效，手动刷新失效 |
| 文件空间摘要 | 256 / 2 MiB；同父目录最多 8 条、512 KiB | 10 秒；Web 文件操作显式失效，外部修改由 TTL 兜底 |
| 首页概览 | 每个 Web 服务实例 32 / 8 MiB；每用户最多 4 条、2 MiB | 0.5 秒，用户/来源/会话独立键 |

同一键并发缺失只运行一个加载器；不同键的磁盘/数据库读取不持有全局缓存锁。等待任务结束后重新检查缓存，异常不缓存为空结果。每个缓存最多跟踪 128 个进行中的加载，超过预算直接读源、不增加跟踪状态。TTL/LRU 同时限制条目和 Python 对象估算容量，并优先淘汰超出当前用户配额的数据。此容量是缓存驻留快照估算，不是进程总 RSS 上限，也不包含请求正在构建的临时结果。

读快照深拷贝隔离；失效会标记正在读取的任务，禁止旧结果回填。已经开始的请求仍可能收到其读取时的快照，后续读取重新加载。失效标记随任务结束释放，没有无限增长的目录 generation 表。`stats()` 只返回命中、缺失、等待、淘汰、绕过、驻留条目/估算字节及正在加载数，不暴露路径、用户名、正文或密钥，也不新增统计落盘。

源文件缓存保留每次文件元数据检查，减少的是重复打开/读取，不消除所有 stat 或 JSON 解析。读取中变化会重试，持续变化回退直接读取；缺失、权限/编码错误不负缓存。`.env` 不接入缓存。外部写入通常在下次元数据检查可见；外部工具刻意保持所有元数据不变时由 5 秒 TTL 兜底。JSON 每次重新解析，配置校验、权限裁决、目录成员发现、注册代码执行和完整 Prompt 构建不缓存，避免共享可变注册器或冻结用户/会话的动态记忆与权限。

本次不把未持久化的 Cron 状态、执行锁、活跃 Run、删除栅栏、消息幂等状态改为 LRU 缓存，也不推迟新的业务写入。模型能力/网络目录等其他专用缓存暂保留原策略；跨进程依赖文件签名/短 TTL 或数据库事务，没有分布式缓存一致性承诺。高频成功与重复 partial 聚合使用 300 秒窗口，错误、异常指纹变化、恢复、终态与用户操作仍立即持久化。

框架采用“运行态内存优先、语义变化写入、终态事务提交”的持久化策略。它减少高频 Python 任务对 JSON、Markdown 与 SQLite 的重复覆盖，但不延迟错误、取消、对话终态和用户主动操作。

### 高频系统任务

- 感知刷新、拓展刷新和记忆晋升检查仍按原调度频率执行。
- `latest_run_at`、`next_run_at` 与运行状态先保存在进程内；默认每 300 秒、发生错误或 RuntimeHost 正常停止时写回任务 JSON。
- 高频任务的正常完成和无模块可运行的 `skipped` 结果按用户与任务聚合，默认每 300 秒写一条汇总日志；失败和部分失败立即写入。
- 聚合日志保留运行次数、平均/最大耗时、窗口起止时间与最后一次有界结果摘要，不保存 Prompt 或大正文。

### 感知与拓展采集

- 采集进程仍按设定频率运行，System Prompt 读取的仍是最新已采集结果。
- 数据 Markdown、JSON 和二进制图表只有在语义内容改变时才原子替换。
- 健康状态发生变化时立即写清单；健康状态稳定时最多每 300 秒更新一次检查点。
- 新建感知/拓展模板不再把当前秒级时间写进注入正文，避免“数据没变、文件必变”。

### 对话与记忆

- archive 正文由 `history_messages` 唯一保存；逐轮的思考、工具、Item 与指标由 `history_rounds` 保存。schema v3 会自动迁移旧窗口 JSON，不丢失消息或轮次分区；schema v4 会创建删除会话栅栏，schema v5 会创建物理窗口 tombstone，不需要人工改库。
- 正常提交新一轮只追加 archive 的新增消息后缀和一个 round 行；编辑或撤回旧正文才显式重建对应 archive 增量行。兼容 runtime 快照若被显式重写，裁剪位移会复用至少 80% 的旧行，只迁移保留尾部并追加新尾行。
- 一轮终态的 archive、上下文摘要、会话索引与活跃绑定在同一个 SQLite 事务中提交。任一持久化部分失败会整体回滚；runtime 缓存只在事务成功后更新。
- 普通终态已经写入 `run_state=idle` 时，清理阶段重复设置相同状态和相同 Run ID 会直接返回，不再产生第二次会话索引写事务；Cron 完成时间和租约分支不参与该短路。
- 记忆完成、失败、排队等状态只更新 archive `data_json` 和会话索引，不重写消息、思考、工具与 Item 大分区。

### 不进入内存延迟的边界

以下内容仍立即持久化：错误与部分失败日志、对话成功/取消/失败终态、用户主动创建或修改任务、文件和媒体产物、外部消息幂等状态、记忆碎片正文，以及需要跨重启继续的任务声明。
