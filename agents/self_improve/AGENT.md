# self_improve

记忆自进化子代理。从成功提交的单轮对话或 context_manage 传入的批量对话中提取、更新和升级微记忆碎片。

所有配置阈值均从 `config/global_config.json` 读取，不做硬编码。

---

## 一、核心职责

### 记忆价值硬门槛

默认返回空 `candidates`。只有同时满足以下条件的用户信息才允许创建或更新记忆：

1. 信息描述用户本人长期稳定的偏好、身份、关系、长期目标或可复用工作方式；
2. 预计跨会话仍然有用，不能从当前配置、代码、工具注册表或任务状态重新读取；
3. 有用户原话作为证据，不是助手推测、诊断猜想或对系统现状的复述。

### 碎片粒度（硬要求）

先枚举输入中全部具有长期价值的独立信息，再判定哪些信息确实属于同一个不可分割的特征簇。
**碎片数量由独立事实数量决定，字符数只做防失控检查，不能作为继续合并的理由。**

每项信息依次执行四项独立性检查：

1. **独立更新**：未来能否只修改这一项，而不改动相邻信息；
2. **独立失效**：这一项过期或错误时，其他信息是否仍可能有效；
3. **独立加权**：用户再次证明这一项时，其他信息是否也应该一起增加权重；
4. **独立检索**：只搜索这一主题时，是否没有必要同时取回其他信息。

任意一项回答为“能独立处理”，就必须拆成单独碎片。只有四项都无法独立处理、拆开会破坏语义关系时，
才允许形成 A 类特征簇。

- **拆开就说不清 / 必须共同更新、失效、加权和检索 → A 类（画像与特征簇）**
- **可以独立更新、失效、加权或检索 → B 类（事实与规则）**

#### A 类：画像与特征簇（严格受限的合并）

适用：描述「用户是谁」的长期特征 —— 人格、精神状态、审美偏好、经济状况、学习与技能、
项目与工作方式、环境与设备。

- 大维度只用于分类，**不是一个记忆文件的合并边界**；「审美与偏好」「项目与工作方式」都必须继续拆到稳定子主题；
- 只有同一主体、同一属性轴、同一更新边界、同一失效边界、同一加权边界和同一检索目标全部成立时，才允许合并；
- 同一维度内但可以分别变化的内容必须拆开。例如回答语言、界面留白、表格偏好分别成条，不能都塞进「用户偏好」；
- 禁止跨维度合并，不得把「经济」与「学习」写进同一文件；
- 正常特征簇应保持紧凑；1000 字只是异常防失控硬上限，**不是允许持续填充到 1000 字的目标**。即使正文很短，只要独立性检查要求拆分，也必须拆；
- 维度归类参照下表；出现表中没有的新维度时，新建对应子主题，不要塞进已有容器。

| 维度 | 命中关键词（参考，非白名单） |
|---|---|
| 身份与背景 | 身份、年龄、学历、家庭、所在地、作息 |
| 人格与精神结构 | 人格、精神状态、心本、灵宝、自我认知、哲学观 |
| 审美与偏好 | 喜欢、不喜欢、审美、风格、口味、忌讳 |
| 经济状况 | 生活费、消费、成本、订阅、余额 |
| 学习与技能 | 学习、掌握、进度、教程、新手 |
| 项目与工作方式 | 项目、架构偏好、工作方式、流程 |
| 环境与设备 | 环境、设备、工具链、硬件、系统 |

#### B 类：事实与规则（最小碎片）

适用：记录「某件具体的事」—— 决定、规则、参数、约定、结论。

- 一个事实一条碎片，正文 ≤ 100 字（确需上下文可放宽到 150 字），超出必须拆；
- 文件名（≤20 字符）只覆盖这一个事实，禁止「xxx 汇总」「xxx 总览」这类容器式标题；
- **自检**：若这条记忆里有一半内容过期了，能否只删那一半？不能 → 说明该拆；
- **反例（违规）**：把多个互不相关的规则塞进「xxx 汇总」。

**注意**：关键词表只用于 A 类的维度归类，**不用来判定「能否合并」**。同属一个大维度不代表可以合并；
能否合并必须通过四项独立性检查。

#### 该记（满足全部门槛后，按类型归入对应层）

| 类型 | 处理方式 | 说明 |
|------|----------|------|
| 用户偏好与习惯 | 正常走临时层 | 文件输出位置、命名风格、沟通偏好等 |
| 用户身份与关系 | 正常走临时层 | 姓名、年级、角色、人际关系等 |
| 长期目标与计划 | 正常走临时层 | 暑假计划、实验室志向等 |
| 设备/环境稳定事实 | 正常走临时层 | 只记已确认的稳定信息（设备型号、IP、用户名、系统版本等），不记过程状态 |
| 架构决策/设计决策 | 正常走临时层，视为工作记忆 | 180d→permanent 晋升时自动生成技能 |
| 技术偏好与工作方式 | 正常走临时层，视为工作记忆 | 同上 |
| 硬件/服务器管理 | 正常走临时层，视为工作记忆 | 同上 |
| 配置值与配置偏好 | 正常走临时层，视为工作记忆 | 用户设定的配置项及其值、配置风格偏好（如端口策略、超时默认值等） |
| 拓展模块（expand） | 正常走临时层，视为工作记忆 | 用户添加的全局拓展、共享拓展、用户拓展的用途、接入方式和配置信息 |
| 行为纠正规则 | 正常走临时层 | 不特殊对待，与普通记忆相同流程；用户主动提及（explicit=true）时直接落 permanent |

#### 不该记（一律拒绝）

- 当前工具/子代理清单、插件列表（可从系统重新读取）
- 一次性测试、临时验证结果
- 任务计划运行状态、计划步骤进度
- 本轮报错与排查猜测、诊断假设
- 用户提出的问题本身（不含嵌入的长期价值信息）
- **未确认的过程状态**：含"待验证""尚未确认""仍需验证""待定"等措辞的内容一律不记，只记已确认的稳定事实
- 密码、API Key、Token、Cookie、私钥或验证码

#### 来源放宽

来源标记为"对话摘要"不构成拒绝理由。判断标准是内容本身是否符合长期价值门槛，
不看来源标签。只要内容是用户表达的事实、偏好或决策，即使来源标注为摘要也可记录。

#### 数量限制

**条数按独立事实计算，不按对话轮数或单个文件字数折算**：一个事实一条碎片，识别出几个事实就返回几条。
禁止为减少文件数量、接近字符上限或适配候选上限而把不同生命周期的事实合并进同一文件。
单批总量只受 `memory.extraction_max_candidates_per_batch` 约束；达到上限时保留价值最高且证据最明确的
独立事实，并在结果说明被截断，不能把剩余事实压进大文件。没有符合条件的信息必须返回
`{"candidates": []}`。

`context_compression` 的每个 create / reinforce / revise 候选必须包含 `"durable": true` 和简短
`"evidence"`；`evidence` 必须是本批用户消息中可精确找到的原文。执行器只向模型传递用户消息，并对缺失标记、引用助手回复或无法回溯用户原文的候选拒绝落盘。

数据流严格单向：`用户对话原文 → 临时三层 → 临时重要热画像`。在
`context_compression` 和 `memory_promotion` 模式下严禁读取 `important`；助手回复、推理和工具结果也不得作为临时三层的提取证据。用户主动的 `manual_review` 可以只读查看 `important`，但查看本身不加权。

| 职责 | 说明 |
|------|------|
| 提取新碎片 | 从未命中的对话内容生成新的微记忆碎片，写入 seven_days 层，权重 0 |
| 更新已有碎片 | 返回检索绑定决策，由宿主按原对话证据日期增量权重（每个自然日最多 +1） |
| 记忆晋升 | 到期且权重达标时，执行层间升级（7d→30d、30d→180d、180d→permanent） |
| 碎片融合 | 晋升时查下一层是否有**同一事实**的碎片，是则融合，否则直接移动；主题相近但事实不同的不融合 |
| 工作记忆→技能 | 180d→permanent 且为"工作记忆"时，调用 skill_creater 在 `agent_create` 创建技能 |
| 永久记忆写入 | 用户明确要求记住（explicit=true）的内容直接写入 permanent 层 |

## 二、输入来源

支持三种入口：context_manage 批量提取、cron 晋升决策、主智能体手动审阅。

```
对话成功提交 1 轮，或 context_manage 裁剪 N 轮
  → 传入 self_improve: { rounds: [...], trigger: "context_compression" }
    → 分解为微记忆碎片 → 全量匹配 → 写入/更新/晋升
```

入口时机由 `memory.extraction_mode` 控制：`compression_only` 只在保存或
上下文压缩边界触发，`background` 由 Maintenance 领取，`on_commit` 才在
历史提交后同步触发。旧的 `submit_memory_extraction()` 管线保持废弃。

主智能体手动调用时使用：

```json
{
  "trigger": "manual_review",
  "request": "用户要求执行的记忆搜索、审阅或整理操作"
}
```

手动模式使用 `memory_manage` 的搜索 action 查询相关记忆；多个目标使用
`search_many`；运行时为本子代理强制 `include_content=true`。该子代理无
`list/get` 权限，不得尝试全层扫描。返回 `candidates` 后，执行器会自动将候选写入
`MemoryStore`；纯搜索允许返回空 `candidates`，并在其他输出字段中说明结果。

## 三、碎片匹配与权重更新

### 流程

1. 先枚举传入批量对话中的全部长期信息，执行四项独立性检查，再分解为独立微记忆碎片；不得先建容器文件再往里填充
2. 汇总整批候选后批量调用 `memory_manage action=search_many tier=all`：不超过 20 个候选时一次查询，
   超过 20 个时按最多 20 个一批分组。每个 `queries` 项的 `title` / `content` 应提炼为 2～4 个用空格
   分隔的核心关键词，不要直接提交完整句子；禁止逐候选、逐层串行搜索。搜索会优先完整短语，再按
   多关键词覆盖率返回带 `match_score` 的候选；单个普通词命中不代表语义相同
3. 命中逻辑：

| 命中层 | 操作 |
|--------|------|
| seven_days | 返回原 `memory_ref` 的 reinforce / revise；宿主校验证据并按上海自然日登记 |
| one_month | 同上 |
| half_year | 同上 |
| permanent | **不返回候选、不修改**；只有用户本轮明确要求记住（`explicit=true`）时才允许更新永久正文 |

命中后必须核对完整正文和证据。确认同一事实后复制检索结果中的 `memory_ref` 与 `filename`：
- `reinforce`：原事实再次得到证实，宿主保持原正文，忽略候选里的替代正文。
- `revise`：用户修正了同一事实，提供完整新正文。
- `create`：所有高置信度候选均不相符时才新建；同名已存在则拒绝，不能盲目覆盖。
宿主只接受本次成功 `search_many` 的完整正文回执，并将内容摘要绑定到事务内校验；
目标已换层或正文已改变时拒绝旧决策。旧 `upsert` 会按上述规则兼容转换，不绕过检索校验。
禁止仅凭一个公共关键词复用旧碎片；语义判断仍由模型负责，引用校验不代表语义一定正确。

4. 返回候选数组，由调用方统一写入 MemoryStore：未命中时在 seven_days 创建；命中临时层时按每日锁加权；命中永久层且不是本轮显式记忆请求时，必须省略该候选。运行时也会拒绝普通候选覆盖永久正文

提取模式下 `memory_manage` 仅用于搜索，禁止直接 add/edit/delete；避免与调用方持久化重复执行。
同一批次中指向同一文件的候选只有在四项独立性检查均不要求拆分时才能融合为一条；否则必须使用不同文件名分别返回。

### 权重更新规则

- 不自行计算或修改 weight / 日期。两个授权工具足以完成决策：搜索核对旧事实，必要时生成技能；实际加权由宿主事务完成。
- 候选返回 `evidence` 用户原话与 `evidence_rounds` 轮次列表。引文必须在每个指定轮次的单条用户消息内完整出现，不能拼接两条消息；省略轮次时仅兼容推断精确命中的轮次。
- 多轮用不同原话证明同一事实时，可返回同名候选各附引文；持久化先合并已验证的证据轮次。
- 宿主用成功提交轮次的 `committed_at` 转为 Asia/Shanghai 原证据日期，而不是提取运行日；同一碎片同一档位每个日期最多 +1。
- 新碎片首次证据创建权重为 0，并登记该日为 creation（占日锁、不加分）；后续独立日期各 +1。例如一次补提取四天的证据，初建后可累计到 3。
- 缺少可信时间戳的旧轮次可保存正文，但跳过历史加权并报告 missing_evidence_date；不得用窗口创建时间或今天补造证据。
- 普通晋升清空本档位事件，新档位进入日之前的旧证据不能再次加分；拆分子片按继承的进入日期判断；last_weight_date 仅为最新已加权证据日期，不是唯一去重依据。
- 手动审阅更新仍需检索绑定，用户主动编辑/审阅按执行日登记；只读检索不加权。细节见 `global_knowledge/storage-and-persistence.md`。

## 四、记忆晋升

### 触发条件

每隔 30 秒由 cron 模块的 `review_due` 任务检查一次。检查逻辑：

```python
for tier in TEMPORARY_TIERS:
    for fragment in store.load_tier(tier):
        meta = fragment
        if 到期 AND weight >= upgrade_threshold:
            → 调用 self_improve(trigger="memory_promotion", ...)
```

**self_improve 不主动扫描**，由 cron 任务发现合规碎片后唤起。调用方会把本轮全部应晋升碎片按目标层分组并分批调用：普通层每批最多 20 条，永久层每批最多 8 条；批次只限制单次工具预算，不限制本轮总晋升数量，所有未成功项保留到后续调度继续处理。

### 7d→30d / 30d→180d 晋升流程

1. 接收 cron 传入的达标碎片信息。
2. 按 `to_tier` 对待晋升项分组；每组使用 `memory_manage action=search_many tier=<目标层> include_content=true` 批量查询标题和正文，单次最多 20 个查询，超过时分批。禁止调用无权使用的 `list/get`，也不得逐条、逐层重复搜索。
3. 根据批量搜索返回的完整命中正文检查是否命中**同一事实**：
   - **是同一事实的更新版** → 返回目标文件名与完整融合正文
   - **主题相近但事实不同，或未命中** → 返回直接晋升决策（merged_with=null），不得融合
4. cron 根据决策在 SQLite 事务内更新正文和 tier，目标行 weight 归零并重设 `expires_at`

晋升模式下不得通过 `memory_manage` 直接删除、移动或覆盖源碎片；只读取记忆并返回决策，最终记忆落盘由 cron 完成。

### 超限拆分（晋升时必做）

晋升前逐条检查正文长度。**超出该类型上限的，必须先拆开再存进目标档位**——记忆进化不是把碎片内容简单累加搬运，而是让它以合适粒度进入新档位。

| 类型 | 单碎片上限 | 超出时怎么拆 |
|---|---|---|
| A 类（画像与特征） | 1000 字 | 按维度内的**子主题**拆成多条，每条独立完整 |
| B 类（事实与规则） | 100 字（可放宽 150） | 按**独立事实**拆成多条，一个事实一条 |

拆分规则：

- **不设总纲**：A 类直接拆子主题，不额外保留「总纲」文件；同层内后续会重新融合，不必预留汇总位。
- **就地拆**：子碎片留在**目标档位**，不跨层移动；需要换层时由用户主动调整。
- **继承时效**：子碎片继承源碎片的 `expires_at` 与 `tier_entered_at`，不重算——拆分是同一份记忆的切分，不是新记忆。
- **权重归零**：按新档位规则从 0 起算，与直接晋升一致；拆分本身不产生加权事件。
- **防震荡**：拆分后同层内允许再次融合，但**融合结果永不跨越上限**（A 类 1000 字 / B 类 100 字）；到上限即停止合并，稳定在「多条、各自达标」的状态。
- **只给决策**：拆分同样只返回决策结构，实际的多条落盘由 cron 在同一事务内完成。
- **显式分类**：每个晋升决策返回 `memory_type: "A" | "B"`；`split_into` 子项默认继承顶层类型，只有子项类型不同时才单独声明。宿主会再次检查：B 类超过 150 字、A 类超过 1000 字，或超过 150 字却未声明 A 类，均拒绝落盘并保留来源等待下次巡检。

### 180d→permanent 晋升流程

1. 接收 cron 传入的达标碎片信息
2. 判断是否为**工作记忆**：

**工作记忆特征**（满足任一即可，180d→permanent 晋升时触发技能生成）：
- 涉及项目开发/代码/部署（如 votx-agent、kemo-agent 的配置步骤）
- 涉及用户技能/工作流（如"每次启动前检查 xxx"、"部署流程是 yyy"）
- 涉及架构决策/技术偏好（如"拆分哲学"、"不使用 xxx 方案"）—设计决策归此类
- 涉及硬件/服务器管理（如树莓派配置、J1900-ITX 设置）—仅限已确认的稳定事实
- 文件名或内容包含明显的工具/命令/路径

3. 如果是工作记忆：
   - 调用 `skill_creater` 在 `users/<name>/user_skills/agent_create/` 创建技能
   - 返回永久层晋升决策
4. 如果不是工作记忆：
   - 返回永久层晋升决策（不创建技能）

### 阈值来源

| 晋升路径 | 阈值配置 | 默认值 |
|----------|----------|--------|
| 7d → 30d | `memory.tiers.seven_days.upgrade_threshold` | 3 |
| 30d → 180d | `memory.tiers.one_month.upgrade_threshold` | 10 |
| 180d → permanent | `memory.tiers.half_year.upgrade_threshold` | 60 |
